# Backend-спецификация — Sensor Watch

[README](../README.md) · [Техническая спецификация](TECHNICAL-SPEC.md) · [Frontend](FRONTEND-SPEC.md) · [HTTP API](../gateway/README.md)

Backend состоит из движка и FastAPI gateway. JS-движок [demo/engine.js](../demo/engine.js) работает как UMD-модуль в браузере (`SensorDemo`) и Node.js (`require`). Python-порт — [gateway/app/engine](../gateway/app/engine/). Формулы и правила решений заданы в [технической спецификации](TECHNICAL-SPEC.md#алгоритмы-монитора).

## Generator — генератор синтетических данных

JS: `generate(scenario = 'combined', seed = 42)`. Python: `generate(scenario='combined', seed=42)`. Результат — Dataset; неизвестный сценарий или недопустимый seed вызывают ошибку.

```typescript
type ScenarioID = 'combined' | 'spike' | 'drift' | 'gap' | 'mode';
type Message = {
  id: number;             // модельная секунда измерения
  sensor_id: string;      // camera-01
  event_time: number;     // модельные секунды
  received_at: number;    // модельные секунды, может быть дробным
  value: number;          // без ограничения диапазоном 0…100
  mode: 'A' | 'B';
  quality_flags: string;  // генератор выдаёт valid
};
type Truth = {
  start: number; end: number;
  type: 'quality' | 'availability'; label: string;
};
type Annotation = {
  start: number; end: number; label: string;
  kind: 'spike' | 'quality' | 'availability' | 'batch' | 'mode';
};
type Dataset = {
  scenario: ScenarioID; seed: number; duration: number;
  messages: Message[]; truth: Truth[]; annotations: Annotation[];
};
```

`duration` — последняя модельная секунда; генерация идёт от 0 до duration включительно. До исключения сообщений пропуска это duration + 1 измерений. `messages` отсортированы по `(received_at, event_time)`.

### Генерация и детерминизм

- PRNG — **mulberry32** с 32-битной арифметикой; Python воспроизводит JS-операции.
- Нормальный шум — преобразование Бокса — Мюллера, σ = 1,5. Среднее берётся из профиля режима.
- Деградация — линейное снижение до −12 относительно среднего, затем удержание и восстановление за 20 с.
- В пропуске часть измерений доставляется около `batchTime` со сдвигом `random() × 0.5 − 0.25 с`; последние 15 с перед пачкой и остаток пропуска не генерируют доставляемых сообщений.
- Одинаковые сценарий и seed дают одинаковый Dataset. Seed — целое число 1…999999; он меняет шум, а не расписание событий.

### Сценарии

Все отметки — модельные секунды. Интервалы событий имеют исключённую правую границу.

| ID | Длительность | События |
|---|---:|---|
| `spike` | 120 | Значение 40 на t = 60, размеченной неисправности нет |
| `drift` | 220 | Снижение с 60 до 110, удержание до 150, восстановление до 170; truth качества [60, 170) |
| `gap` | 160 | Truth свежести [60, 120), пачка около 110, свежий поток с 120 |
| `mode` | 150 | Режим B с t = 60, размеченной неисправности нет |
| `combined` | 390 | Выброс 60; снижение 100→160, удержание до 180, восстановление до 200; пропуск [240, 300), пачка около 290; режим B с 340 |

`truth` нужна оценщику, `annotations` — визуализации. Монитор получает только сообщения и текущее время.

## Monitor — потоковый детектор

JS: `new Monitor().tick(now, incoming)`. Python: `Monitor().tick(now, incoming)`, результат преобразуется через `Frame.as_dict()`. Вызывающая сторона должна подавать сообщения в порядке доставки и продвигать часы, включая такты без сообщений. У монитора нет HTTP-зависимостей.

### Состояние

| Поле JS / Python | Содержание |
|---|---|
| `mode`, `s`, `z` | Последний режим, CUSUM и стандартизованная медиана |
| `recent` | До пяти последних рассчитанных z |
| `buckets` | По номеру окна: нормированные остатки `r[]` и последний известный режим |
| `badBuckets` / `bad_buckets` | Число невалидных сообщений по окнам |
| `lastBucket` / `last_bucket` | Последнее закрытое окно |
| `seen` | Номер временной корзины → множество ID, горизонт 120 с |
| `newest`, `lastReceipt` / `last_receipt` | Новейшее пригодное измерение и время последнего недублирующегося приёма |
| `qualityIncident`, `availabilityIncident`, `flagsIncident` / snake_case | Ссылки на независимые открытые инциденты |
| `freshRun`, `flagsOkRun` / snake_case | Подтверждения восстановления свежести и флагов |
| `incidents`, `events` | Ограниченные списки инцидентов и решений |

### Кадр статуса

| JS | Python / HTTP | Значение |
|---|---|---|
| `now`, `mode` | Те же имена | Время такта и строка режима, `—` до первого обработанного сообщения, задающего режим |
| `modeKnown` | `mode_known` | Для режима есть эталон |
| `s`, `z` | Те же имена | CUSUM и последнее z |
| `aggregate` | То же имя | Медиана остатков в шкале последнего режима окна, либо null |
| `aggregateTime` | `aggregate_time` | Время агрегата, либо null |
| `quality` | То же имя | `normal`, `suspect`, `alarm`, `unknown` |
| `availability` | То же имя | `fresh`, `stale`, `unknown` |
| `flags` | То же имя | `ok`, `degraded` |
| `age` | То же имя | Возраст новейшего пригодного измерения, либо null |
| `sinceReceipt` | `since_receipt` | Время после последнего приёма, либо null |
| `lateCount` | `late_count` | Сообщения, исключённые по опозданию / закрытому окну |
| `accepted` | То же имя | Обработанные недублирующиеся сообщения, включая невалидные и поздние |
| `events` | То же имя | Текущая длина внутреннего журнала, не пожизненный счётчик |

Счётчик `accepted` кадра отличается от `accepted` ответа `/telemetry`: HTTP считает поставленные в очередь сообщения до дедупликации.

### Инциденты и журнал

Инцидент движка: `{id, type, start, end, reason}`. `type` — `quality`, `availability` или `flags`; `end = null` означает открытый инцидент. ID последовательно назначается внутри одного монитора.

Событие: `{time, kind, type, text, incident_id?}`. `kind` — `open`, `close`, `mode`, `unknown_mode`; для двух последних `type = 'info'`. Python-порт дополнительно вызывает `on_event`, если задан обработчик: gateway использует его для собственного журнала. Gateway дополняет события полями `seq`, `sensor_id`, `wall_time`, инциденты — полями состояния и Unix-времени открытия / закрытия.

## Replay — полный проход

`replay(scenario, seed)` генерирует Dataset и создаёт отдельный Monitor. На каждом целом `now` от 0 до duration забирает ещё не обработанные сообщения с `received_at ≤ now`, вызывает `tick`, сохраняет Frame. Дробное время доставки пачки округляется вверх фактически выбранным тактом; фильтрации по точному равенству времён нет.

Результат — поля Dataset плюс `frames`, `incidents`, `events`, `baseline`. Replay не передаёт разметку монитору. Автономный интерфейс воспроизводит уже рассчитанные кадры; gateway может пройти ту же последовательность в живой симуляции.

Пороговый метод проверяет последнее свежее измерение такта: открывает качество при `value < μ − 4.5σ`, закрывает при возвращении к порогу или выше. Свежими для этого сравнения считаются сообщения возрастом ≤ 5 с. Инциденты доступности копируются из монитора, собственного таймера у порога нет.

## Evaluator — метрики

`evaluate(result)` возвращает `{monitor: Metrics, baseline: Metrics}`. Оцениваются `quality` и `availability`; `flags` не входит. Инцидент соответствует событию того же типа, если открылся в `[truth.start − 3 с, truth.end)`.

| HTTP / JS | Определение |
|---|---|
| `detected`, `total` | События с первым соответствующим инцидентом / все размеченные события |
| `false_alarms` / `falseAlarms` | Инциденты без соответствующего события |
| `repeats` | Дополнительные открытия для уже найденного события |
| `unclosed` | Незакрытые ложные инциденты и инциденты событий, закончившихся до конца записи |
| `delay` | Среднее `max(0, incident.start − truth.start)` по найденным событиям |
| `close_delay` / `closeDelay` | Среднее `incident.end − truth.end` по закрытым сопоставленным событиям; может быть отрицательным |
| `closed` | Число закрытых сопоставленных событий |

Если наблюдений нет, среднее — `null`. Пропуски: `total − detected`. Пакетная проверка суммирует счётчики и взвешивает средние задержки по числу найденных / закрытых событий. В Python доступна `benchmark(scenarios, seeds)`; автономный UI выполняет 250 прогонов циклом `replay → evaluate`.

## Gateway

`Registry` хранит `sensor_id → SensorState`, где каждому сенсору принадлежат монитор, история и очередь телеметрии. Фоновый тикер вызывает реестр с периодом 1 с по умолчанию; симуляции проходят каждую модельную секунду. Replay и benchmark работают с отдельными мониторами в пуле потоков и реестр не меняют.

HTTP-модели заданы в [schemas.py](../gateway/app/schemas.py); ограничения телеметрии, маршруты, SSE, защита операций и настройки — в [справочнике API](../gateway/README.md). Часы и хранение — в [технической спецификации](TECHNICAL-SPEC.md#время-и-симуляции). Рабочие зависимости и команды тестирования — в [руководстве разработчика](DEVELOPMENT.md).

## Проверка соответствия реализаций

Python-тесты запускают JS-движок через Node.js и сравнивают сообщения, кадры, журнал, инциденты и метрики. Отдельные тесты проверяют живые симуляции против replay. Изменения алгоритма требуют обновления обеих реализаций, сборки `demo/index.html` и повторной генерации [отчёта валидации](VALIDATION.md).
