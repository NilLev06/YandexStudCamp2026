# YandexStudCamp2026

**Sensor Watch** — автономная демонстрация решения кейса № 7 «Монитор дрейфа сенсоров и качества восприятия» для Яндекс Студкемпа 2026.

Прототип обрабатывает синтетическую телеметрию, обнаруживает устойчивое ухудшение качества и отсутствие свежих измерений, ведёт журнал инцидентов и сравнивает результат с простым пороговым детектором.

![Демонстрация Sensor Watch](demo/preview-desktop.png)

## Запуск

Скачайте репозиторий и откройте [`demo/index.html`](demo/index.html) в браузере. Этот файл самодостаточен: интернет, сервер и установка зависимостей не нужны. Предварительный просмотр HTML непосредственно на странице GitHub не запускает приложение — файл нужно скачать.

Выберите сценарий и нажмите **«Запустить показ»**. Можно менять скорость и seed, перемещаться по времени или переходить к ключевым событиям кнопками.

При желании запустите локальный сервер из корня репозитория:

```sh
python3 -m http.server 8000
```

Затем откройте `http://localhost:8000/demo/index.html`.

## Сценарии

- Одиночный выброс без устойчивой неисправности.
- Плавная деградация с восстановлением.
- Пропуск данных и доставка накопленной пачки старых измерений.
- Допустимая смена режима.
- Полная последовательность событий для защиты.

Seed меняет случайный шум. Типы и время событий определяются сценарием. Одинаковый seed воспроизводит одинаковые данные. Допустим целый seed от 1 до 999 999. Если ввести другое значение, интерфейс покажет ошибку и оставит текущий поток.

Рядом с запуском показаны рекомендуемые seed для выбранного сценария: эталонный 42 из сценария защиты и граничные случаи — самое быстрое и самое медленное обнаружение, инцидент, который не успевает закрыться, и наибольший CUSUM без тревоги. Рекомендации выбраны прогоном seed 1…1000, тесты проверяют каждую.

## Алгоритм

- Обработка измерений по времени доставки с разделением времени измерения и получения.
- Медиана неперекрывающихся окон 3 с, ожидание опозданий 2 с. Остаток каждого измерения нормируется эталоном его режима, медиана стандартизуется по числу значений в окне.
- Ограниченный CUSUM с подтверждением открытия инцидента по последним окнам. Смена режима не сбрасывает накопление и не закрывает открытый инцидент.
- Подтверждение восстановления по пяти нормальным окнам, затем сброс накопления.
- Независимый таймер свежести: старые сообщения не означают восстановление потока.
- Отдельные заданные эталоны для известных режимов. Неизвестный режим отмечается в журнале, качество в нём не оценивается.
- Отдельный инцидент, если в окне не меньше 50% измерений с невалидными флагами.
- Удаление дублей в пределах окна 120 с: память монитора не растёт с длиной потока.

Разметка не передаётся детектору. Интерфейс воспроизводит результат последовательного прохода по потоку; при расчёте детектор не получает будущие сообщения.

## Проверка и сборка

Нужен Node.js 18 или новее. Сторонние пакеты не требуются.

```sh
node --test demo/engine.test.cjs
node demo/build.cjs
node demo/validate.cjs   # отчёт docs/VALIDATION.md
```

Сборка встраивает движок в интерфейс и обновляет `demo/index.html`.

В интерфейсе доступна пакетная проверка: 5 сценариев × 50 seed. Для каждого метода считаются обнаруженные и пропущенные события, ложные инциденты, повторные открытия, незакрытые инциденты, средняя задержка обнаружения и закрытия. Результат отдельного сценария можно экспортировать в JSON.

В тестах есть матрицы: сценарий × seed, граница seed × точка входа, проверка каждой рекомендации, величина ступени × seed, длинные здоровые потоки. Отчёт [`docs/VALIDATION.md`](docs/VALIDATION.md) — валидация на 5 сценариях × 1000 seed, ступенчатых снижениях и разных моделях шума.

## Gateway и веб-интерфейс

Помимо автономной демонстрации, в репозитории есть серверная часть:

- `gateway/` — FastAPI: приём телеметрии, потоковый монитор на каждый сенсор, инциденты, журнал, симуляции сценариев, воспроизведение и пакетная проверка, живые обновления через SSE. Подробности и полный список API — в [`gateway/README.md`](gateway/README.md).
- `frontend/` — React + [Gravity UI](https://gravity-ui.com): `@gravity-ui/uikit`, `@gravity-ui/navigation`, графики `@gravity-ui/charts`.

```sh
# терминал 1
cd gateway && python3 -m venv .venv && .venv/bin/pip install -r requirements-dev.txt
.venv/bin/uvicorn app.main:app --port 8000

# терминал 2
cd frontend && npm install && npm run dev
```

Интерфейс: `http://localhost:5173`. Vite проксирует `/api` на gateway. Для одного процесса выполните `npm run build`: gateway сам раздаст `frontend/dist` на порту 8000.

## Новые кейсы в React

После запуска gateway и React доступны два раздела:

- `/single` — **Один датчик**: 15 воспроизводимых сценариев и восемь независимых тревог: отклонение уровня в обе стороны, повышенный разброс, подозрение на залипание, насыщение, снижение частоты, непригодные измерения (включая невозможные скачки), отсутствие свежих данных, высокая доля опоздавших сообщений. Каждая тревога содержит наблюдаемый признак, порог и условие подтверждения; восстановление записывается отдельно.
- `/pair` — **Два датчика**: общая динамика, дрейф одного канала, одиночный выброс и пропуск со старой пачкой. Расхождение подтверждается одним окном 3 с с минимум тремя новыми синхронизированными парами; восстановление — двумя нормальными окнами подряд, всего 6 с. Монитор не определяет виновный источник.

Оба раздела используют FastAPI и React + Gravity UI, поддерживают seed, воспроизведение, перемещение по времени и журнал. Основной интерфейс работает с симуляциями: вкладка обзора и страницы реальных сенсоров убраны из маршрутов. В `/analysis` доступны полная демонстрация, 15 отдельных сценариев одного датчика и 4 сценария пары с актуальными правилами тревог. Сценарий и seed автоматически загружают расчёт; графики используют модельное время мин:с и синхронное наведение. Проверка на разных seed отдельно показывает обнаружения, пропуски, лишние тревоги вне заданных событий, повторные открытия, ранние снятия и незакрытые тревоги. Каждый прогон можно открыть в разборе. Вкладка «Тревоги» хранит последние 30 рассчитанных симуляций в браузере. Служебные API телеметрии сохранены для совместимости; исторические `/replays`, `/benchmark` и автономный `demo/index.html` используют прежний сравнительный алгоритм и не используются текущей вкладкой анализа.

В `/single` основной график показывает измерения и норму режима; медиана включается отдельно. Нижний график показывает CUSUM, разброс вынесен в числовой показатель. Медиана уровня считается в неперекрывающихся окнах 3 с. Для уровня используется двусторонний ограниченный CUSUM с параметрами исходного монитора: k=0.5, h=10, clip=4.5, подтверждение по одному текущему окну после достижения порога; восстановление — два нормальных окна подряд по 3 с и сброс накопления. Подтверждённое оба нормальных окна не закрашиваются красным; время решения о закрытии остаётся в журнале. Динамика и полнота оцениваются в окнах 3 с, открытие — одно нарушенное окно, закрытие — два нормальных окна подряд. Для разброса требуется минимум три пригодных измерения; два нормальных окна подряд могут закрыть тревогу до окончания всего шумного интервала. Для непригодных значений достаточно одного окна с долей ≥50% и минимум двумя сообщениями; восстановление — два нормальных окна подряд по 3 с. Свежесть восстанавливается по двум нормальным окнам подряд по 3 с с минимум шестью новыми пригодными измерениями. Старые сообщения не подтверждают восстановление. Невозможный скачок исключается из расчёта уровня и разброса и учитывается в доле непригодных сообщений.

Профиль `/single`: диапазон 0…100, допустимая скорость изменения 12 ед/с, ожидаемый период 1 с, нормы A: 70 ± 1 и B: 50 ± 1. Залипание имеет смысл только при ожидаемой динамике (настраиваемый `min_spread`, 0 отключает проверку). Насыщение и невозможная скорость требуют известных физических ограничений. Повышенный разброс не доказывает случайный шум; одиночный канал не устанавливает физическую причину изменения. Отдельная классификация квантования, ошибки масштаба и дрейфа нуля не реализована.

# Опционально: Playwright установлен, gateway запущен на 8010

## Ограничения

Текущая версия использует синтетические данные, заранее заданные эталоны и согласованные часы. Автоматическая калибровка и подключение оборудования не реализованы. Сравнение с порогом иллюстративное, без выравнивания бюджета ложных тревог; результаты не доказывают пригодность для реального оборудования.

Реальные наборы данных не подключены. Gateway хранит состояние в памяти одного процесса.
