# Gateway и API

[README](../README.md) · [Архитектура](../docs/TECHNICAL-SPEC.md) · [Детектор](../docs/TECHNICAL-SPEC.md#алгоритмы-монитора) · [Разработка](../docs/DEVELOPMENT.md)

FastAPI-сервис принимает телеметрию, поддерживает монитор каждого сенсора, хранит историю в памяти и отдаёт REST/SSE. Python 3.10+, зависимости закреплены в `requirements.txt`; проверенное окружение — Python 3.12.12.

## Запуск

Из корня репозитория:

```sh
cd gateway
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Для тестов установите `requirements-dev.txt` вместо `requirements.txt`. Он включает рабочие зависимости, pytest и httpx. [Полный запуск с интерфейсом](../README.md#запуск).

- Swagger UI: http://127.0.0.1:8000/docs
- OpenAPI: http://127.0.0.1:8000/openapi.json
- Проверка процесса: http://127.0.0.1:8000/api/v1/health

Готовый `frontend/dist` подключается при создании приложения. Запускайте один worker: общей базы данных у процессов нет.

## Телеметрия

`POST /api/v1/telemetry` принимает JSON с непустым массивом `messages` (до 5000 элементов). Поля сообщения:

| Поле | Формат | Правило |
|---|---|---|
| GET | `/health` | Работоспособность, число сенсоров, симуляций и подписчиков |
| GET | `/meta` | Параметры детектора, эталоны режимов, сценарии, лимиты, границы seed и рекомендуемые seed |
| GET | `/overview` | Сводка статусов и открытых инцидентов по всем сенсорам |
| POST | `/telemetry` | Пачка измерений (до 5000). Ответ `202`: принято и отклонённые с причиной |
| GET | `/sensors` | Список сенсоров с текущим статусом |
| GET | `/sensors/{id}` | Сенсор, эталоны; для симуляции — разметка сценария |
| DELETE | `/sensors/{id}` | Удалить сенсор и историю |
| GET | `/sensors/{id}/frames` | История кадров монитора (`since`, `limit`) |
| GET | `/sensors/{id}/measurements` | Полученные измерения (`since` по времени получения) |
| GET | `/sensors/{id}/events` | Журнал объяснений (`after_seq`) |
| GET | `/sensors/{id}/incidents` | Инциденты сенсора (`type`) |
| GET | `/incidents` | Инциденты всех сенсоров (`sensor_id`, `type`, `state`, `limit`) |
| POST | `/simulations` | Запустить сценарий как живой сенсор |
| GET | `/simulations`, `/simulations/{id}` | Состояние симуляций |
| DELETE | `/simulations/{id}` | Остановить симуляцию; история сохраняется |
| POST | `/replays` | Детерминированное воспроизведение сценария с метриками |
| POST | `/single-replays` | Новый кейс одного датчика: 15 сценариев, восемь независимых тревог с причинами |
| POST | `/pair-replays` | Сравнение 2 или 3 датчиков одной температуры: sensor_count=2/3, четыре сценария в каждом режиме |
| POST | `/benchmark` | Пакетная проверка: сценарии × диапазон seed |
| GET | `/stream` | SSE: `sensor_added`, `sensor_removed`, `update` (параметр `sensor_id`) |

| `sensor_id` | string | 1–64 символа: латиница, цифры, `_ . : -` |
| `event_time` | number | Конечное Unix-время измерения в секундах |
| `value` | number или null | Конечное число; null означает непригодное измерение |
| `mode` | string | Обязательно, 1–32 символа; эталоны есть для `A` и `B` |
| `quality_flags` | string | По умолчанию `valid`; любая другая строка исключает значение из анализа |
| `id` | integer, string или null | Необязательно; ключ дедупликации внутри временной корзины |

Лишние поля запрещены. `received_at` назначает сервер. Пример для текущего времени:

```sh
curl -sS http://127.0.0.1:8000/api/v1/telemetry \
  -H 'Content-Type: application/json' \
  -d '{"messages":[{"sensor_id":"camera-01","event_time":'"$(date +%s)"',"value":95.2,"mode":"A","id":1}]}'
```

Ответ `202`:

```json
{"accepted": 1, "rejected": [], "received_at": 1793221200.0}
```

`received_at` в примере условный. `accepted` означает постановку в очередь, а не пригодность для детектора. Обработка — на ближайшем такте; история измерений уже доступна. Неизвестный сенсор создаётся автоматически.

Слишком будущее время (по умолчанию > 5 с), занятый симуляцией ID и превышение числа сенсоров отклоняются поштучно. В `rejected` возвращаются `index` исходного сообщения, `sensor_id` и `reason`; HTTP-статус остаётся `202`. Некорректная структура хотя бы одного сообщения отклоняет весь запрос с `422`.

## Маршруты

Префикс всех путей — **`/api/v1`**. Точные модели ответов и ограничения полей доступны в OpenAPI работающего сервера.

| Метод | Путь | Результат / параметры |
|---|---|---|
| GET | `/health` | Версия, uptime, число сенсоров, работающих симуляций и SSE-подписчиков |
| GET | `/meta` | Параметры, эталоны, сценарии, seed, лимиты, `auth_required` |
| GET | `/overview` | Число сенсоров по статусам и открытых инцидентов по типам |
| POST | `/telemetry` | Приём пачки, `202` |
| GET | `/sensors` | Сводки сенсоров с последним статусом и открытыми инцидентами |
| GET | `/sensors/{id}` | Сводка, эталоны; разметка и аннотации для симуляции |
| DELETE | `/sensors/{id}` | Удаление сенсора, его истории и симуляции, `204` |
| GET | `/sensors/{id}/frames` | Кадры: `since` по `now`, `limit=3600` |
| GET | `/sensors/{id}/measurements` | Измерения: `since` по `received_at`, `limit=3600` |
| GET | `/sensors/{id}/events` | Журнал: `after_seq`, `limit=500` |
| GET | `/sensors/{id}/incidents` | Инциденты сенсора, необязательный `type` |
| GET | `/incidents` | Все инциденты: `sensor_id`, `type`, `state`, `limit=500` |
| POST | `/simulations` | Создание виртуального сенсора, `201` |
| GET | `/simulations`, `/simulations/{id}` | Список / состояние симуляции |
| DELETE | `/simulations/{id}` | Остановка с сохранением сенсора и истории, `200` |
| POST | `/replays` | Офлайн-воспроизведение и метрики, `200` |
| POST | `/benchmark` | Агрегированные метрики, `200` |
| GET | `/stream` | SSE, необязательный `sensor_id` |

Истории кадров, измерений и событий возвращаются от старых к новым, после фильтрации остаются последние `limit` записей; `limit` от 1 до 10000. `since` и `after_seq` — строгие нижние границы. Общие инциденты сортируются по `opened_at` от новых к старым, `limit` от 1 до 5000.

`type`: `quality`, `availability`, `flags`. `state`: `open`, `closed`. ID инцидента уникален в пределах сенсора; `seq` события — в пределах процесса gateway. `start/end` используют часы сенсора, `opened_at/closed_at` — Unix-время gateway; [подробнее о времени](../docs/TECHNICAL-SPEC.md#время-и-симуляции).

## Симуляции и анализ

```sh
curl -sS http://127.0.0.1:8000/api/v1/simulations \
  -H 'Content-Type: application/json' \
  -d '{"scenario":"combined","seed":42,"speed":6}'

curl -sS http://127.0.0.1:8000/api/v1/replays \
  -H 'Content-Type: application/json' \
  -d '{"scenario":"drift","seed":42}'

curl -sS http://127.0.0.1:8000/api/v1/benchmark \
  -H 'Content-Type: application/json' \
  -d '{"scenarios":["drift","gap"],"seed_from":1,"seed_to":50}'
```

Сценарии: `combined`, `spike`, `drift`, `gap`, `mode`. Seed — JSON integer от 1 до 999999, по умолчанию 42. `speed > 0`, по умолчанию 6, максимум 60; можно задать свободный `sensor_id`. Без ID сервер подбирает имя автоматически.

Replay возвращает сообщения, разметку, кадры, журнал, инциденты, пороговый результат и метрики. Benchmark по умолчанию проверяет все сценарии на seed 1…50; обе границы включены, максимум 1000 прогонов за запрос. Эти операции не меняют реестр и не требуют API-ключа. [Определения метрик](../docs/BACKEND-SPEC.md#evaluator--метрики).

## SSE

```sh
curl -N 'http://127.0.0.1:8000/api/v1/stream?sensor_id=camera-01'
```

| Событие | JSON-поля |
|---|---|
| `sensor_added` | `type`, `sensor_id`, `summary` |
| `sensor_removed` | `type`, `sensor_id` |
| `update` | `type`, `sensor_id`, `summary`, `frames`, `measurements`, `events` |

В начале передаётся `retry: 3000`, при отсутствии сообщений — комментарий `: ping` раз в 15 с. Начального снимка и повторной доставки нет; снимок запрашивается через REST. Медленный подписчик теряет старые обновления после заполнения очереди 256 сообщений.

## Ключ и ошибки

Если задан `GATEWAY_API_KEY`, заголовок `X-API-Key` обязателен для `POST /telemetry`, `POST /simulations` и обоих `DELETE`. Чтение, SSE, replay и benchmark остаются открыты. В браузере ключ передаётся через `VITE_API_KEY` и попадает в клиентскую сборку; это не пользовательская авторизация.

Ошибки имеют оболочку `{"detail": ...}`; `detail` бывает строкой или списком ошибок валидации.

| Статус | Причина |
|---|---|
| `401` | Нет правильного ключа для защищённой операции |
| `404` | Сенсор, симуляция или API-маршрут не найдены |
| `409` | Явно заданный ID симуляции занят |
| `413` | Пачка превышает настроенный `max_batch` |
| `422` | Структура, параметры, seed, сценарий или число прогонов не прошли проверку |
| `429` | При создании симуляции достигнут предел сенсоров |

Схема пачки жёстко ограничена 5000 элементами: более крупный запрос получит `422` до проверки `max_batch`. Настройка позволяет уменьшить фактический лимит, но не поднять его выше 5000. Для телеметрии предел сенсоров отражается в `rejected`, а не в HTTP `429`.

## Настройки

Переменные окружения или `.env` в рабочем каталоге процесса (при запуске выше — `gateway/.env`). Читаются при старте, изменения требуют перезапуска. Списки задаются JSON.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `GATEWAY_API_KEY` | Не задан | Ключ защищённых операций |
| `GATEWAY_CORS_ORIGINS` | `["http://localhost:5173","http://127.0.0.1:5173"]` | Источники браузера |
| `GATEWAY_TICK_INTERVAL` | `1.0` | Интервал тактов, с |
| `GATEWAY_FRAME_HISTORY` | `3600` | Кадров на сенсор |
| `GATEWAY_MEASUREMENT_HISTORY` | `3600` | Измерений на сенсор |
| `GATEWAY_EVENT_HISTORY` | `2000` | Событий на сенсор |
| `GATEWAY_MAX_BATCH` | `5000` | Сообщений в пачке |
| `GATEWAY_MAX_SENSORS` | `1000` | Число сенсоров |
| `GATEWAY_MAX_FUTURE_SKEW` | `5.0` | Допустимое опережение времени измерения, с |
| `GATEWAY_MAX_SIMULATION_SPEED` | `60.0` | Максимальная скорость симуляции |
| `GATEWAY_MAX_BENCHMARK_RUNS` | `1000` | Максимум прогонов за запрос |
| `GATEWAY_STREAM_HEARTBEAT` | `15.0` | Интервал SSE ping, с |
| `GATEWAY_STATIC_DIR` | `frontend/dist` от корня репозитория | Каталог готового интерфейса |

## Ограничения

Одна копия процесса, без персистентности. После перезапуска состояние теряется. Эталоны режимов общие для всех сенсоров и заданы в коде (`app/engine/monitor.py`). Уведомления во внешние системы не отправляются.

## Воспроизведение новых нарушений

`POST /api/v1/single-replays` принимает `{"scenario":"noise","seed":42}`. Сценарии: `normal`, `drift`, `rise`, `step`, `noise`, `periodic`, `stuck`, `saturation`, `spike`, `jumps`, `invalid`, `gap`, `delay`, `rate`, `mode`. Ответ содержит сообщения, кадры, инциденты, журнал объяснений, параметры профиля и отдельную разметку. React-страница: `/single`.

`SingleMonitor` в `app/engine/single.py` работает последовательно по сообщениям и времени обработки. Диапазон, максимальная скорость изменения, частота и ожидаемая динамика задаются профилем. При переиспользовании монитора для оборудования эти параметры нужно обосновать. Ошибки формы/масштаба/нуля отдельно не классифицируются. Допустимы несколько одновременных тревог: плато на границе может вызвать насыщение и подозрение на залипание.

Открытие оконных тревог подтверждается одним полным плохим окном: уровень, доля непригодных измерений, шум, залипание, насыщение, частота и старые сообщения — 3 с. Для уровня дополнительно требуется достижение порога CUSUM 10; одного окна может не хватить для накопления этой суммы. Потеря свежести определяется таймером 6 с. В сравнении двух датчиков одно окно подтверждения расхождения длится 3 с и требует минимум три новые последовательные пары; одиночного выброса недостаточно. Недоступность сравнения определяется отдельным таймером.

`POST /api/v1/pair-replays` принимает `{"scenario":"drift","seed":42}`; допустимы также `normal`, `spike`, `gap`. React-страница: `/pair`. Два расходящихся датчика не позволяют установить виновный источник, а общее смещение обоих может остаться незаметным.

Endpoint `/single-replays` и `/pair-replays` выполняют отдельное синтетическое воспроизведение без изменения registry. Служебные API registry, `/telemetry` и `/simulations` сохранены для совместимости, но основной интерфейс работает только с симуляциями. Все нарушения отображаются как тревоги с причиной. Вкладка `/analysis` использует актуальные сценарии через `/simulation-analysis/cases`, `/simulation-analysis/replay` и `/simulation-analysis/benchmark`. Исторические API `/replays` и `/benchmark` сохраняют исходный алгоритм; текущий интерфейс их не использует. Seed — строго целое число 1…999999. Разметка генератора не передаётся детекторам.

В окне динамики 3 с требуется минимум три пригодных измерения. Допуск размаха для подозрения на залипание — 0.01 единицы профиля. Случайный шум может давать нормальные короткие окна: для восстановления нужны два нормальных окна подряд (6 с); если нормальный участок длится дольше, возможны закрытия и повторные открытия тревоги.

Закрытие всех тревог в `/single` и `/pair` требует двух нормальных окон подряд по 3 с. Для свежести и пары дополнительно нужны минимум шесть новых измерений/пар за период восстановления. Открытие по-прежнему подтверждается одним плохим окном 3 с; порог CUSUM и таймеры недоступности сохранены. После подтверждения оба нормальных окна исключаются из красной подсветки, время решения сохраняется в журнале.

`POST /pair-replays` принимает `sensor_count: 2 | 3` (по умолчанию 2). В ответе есть `sensor_count`, `sensor_ids`; для трёх источников кадры содержат `sensors`, `pairs` (A-B, A-C, B-C) и осторожную гипотезу `suspect_sensor`. Инциденты и события отмечены парой. Анализ включает `triple:normal`, `triple:drift`, `triple:spike`, `triple:gap`; тревоги разных пар не считаются повторными открытиями одной пары.

Параметры детектора и эталоны не переопределяются этими переменными — они заданы в `app/engine/monitor.py`. Пределы хранения и доставки описаны в [архитектуре](../docs/TECHNICAL-SPEC.md#хранение-и-доставка).
